## 1. `llm-revalidate` — Model-retirement-triggered revalidation for GxP LLM applications
**Pitch:** A model inventory + deprecation watcher that opens a change-control record and runs your regression suite whenever a pinned LLM is deprecated or a candidate replacement appears.

**Problem & who needs it:** Validated AI apps (e.g., an internal Claude-based assistant under CSV/CSA) pin a model version; when the provider retires it on ~60 days' notice, QA needs impact assessment, re-testing, and a signed record. Teams currently do this ad hoc in spreadsheets.

**Why now:** Rolling 2026 retirement waves (see signals above; [Anthropic deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations)); FDA/EMA principles emphasize lifecycle management ([overview](https://intuitionlabs.ai/articles/fda-ai-drug-development-guidance)).

**Prior art & gap:** Trackers exist but stop at "alerting": [deprecations/deprecations-rss](https://github.com/deprecations/deprecations-rss) (18★, active), [quora/model-deprecation-tracker](https://github.com/quora/model-deprecation-tracker) (4★), [mnfst/modeldeprecations.dev](https://github.com/mnfst/modeldeprecations.dev) (3★). None links a deprecation to *your* inventory, risk assessment, re-run of tests, and an approval record. That workflow is the gap.

**Why Jerry:** GxP-qualified Bioinformatics Cloud, FCS Express validation, Claude Code tooling at Genentech; he knows what change control actually requires.

**MVP (2–4 wks):** Python CLI + GitHub Action. `models.yaml` inventory (app, model ID, platform, risk tier) → poll RSS/official page → generate a change-request Markdown/Issue with impact checklist → run a pytest/promptfoo-style suite against old vs. candidate model and emit a diff report → require a PR approval as the "signature". Stack: Python, GitHub Actions, Bedrock/Anthropic SDK, Jinja2.

**Career angle:** Concrete artifact for "AI lifecycle management in regulated environments" — a rare, hireable niche in pharma AI governance.

## 2. `omics-sandbox-mcp` — MCP server that runs agent-written analysis in ephemeral, locked-down AWS jobs
**Pitch:** Let an agent execute Python/R against genomics data without giving it your laptop or VPC: each tool call becomes a no-egress Fargate/Batch job with read-only S3 mounts and an audit log.

**Problem & who needs it:** Bioinformatics agents need to run code on sensitive datasets. Local execution is unsafe; generic code sandboxes don't understand S3 data scopes, bio containers, or cost caps.

**Why now:** Agentic data-analysis benchmarks are multiplying (BixBench follow-ups, [BixBench3](https://github.com/EdisonScientific/BixBench3)), and enterprise MCP adoption (Benchling above) raises the bar on data-handling controls.

**Prior art & gap:** Generic MCP sandboxes: [JohanLi233/mcp-sandbox](https://github.com/JohanLi233/mcp-sandbox) (39★, last push Dec 2025), [jeliasson/mcp-sandboxd](https://github.com/jeliasson/mcp-sandboxd) (6★, Docker/K8s). Neither targets AWS Batch/Fargate, per-job IAM scoping, S3 prefix allowlists, or bio images. Open niche.

**Why Jerry:** Built AWS Batch/ECR/IAM/S3 genomics platforms with Terraform; Claude Code + MCP daily.

**MVP:** Python MCP server (`run_python`, `list_inputs`, `fetch_result`); Terraform for a Fargate cluster, VPC with no NAT, per-session IAM role; stdout/artifact capture to S3; JSON audit log; hard time/cost caps. Stack: Python, MCP SDK, Terraform, boto3, Docker.

**Career angle:** Demonstrates "safe agent execution" — the top concern for enterprise AI platform teams. Pairs with idea 3.

## 3. `agent-bench-batch` — Reproducible BixBench-style evaluation for your own agent/model configs on AWS
**Pitch:** Run a bioinformatics-agent benchmark across model versions and agent configs in parallel on Batch, with cost/latency per task and a regression report.

**Problem & who needs it:** Teams choosing between models/skills/prompts for internal bio agents have no easy, reproducible way to compare configs or detect regressions after a model swap.

**Why now:** Benchmark harnesses just landed ([BixBench3](https://github.com/EdisonScientific/BixBench3), 16★, pushed 2026-10-28); skills ecosystems are exploding ([SciAgent-Skills](https://github.com/jaechang-hits/SciAgent-Skills), 390★, claims 92% BixBench); model retirements (idea 1) force re-evaluation.

**Prior art & gap:** [Future-House/BixBench](https://github.com/Future-House/BixBench) (153★, last push Oct 2025) is the benchmark, not an ops harness; [bio-xyz/bio-benchmark](https://github.com/bio-xyz/bio-benchmark) (7★) is single-agent specific. No config-matrix runner with cost accounting and CI gating surfaced. Distinct from earlier `skill-oq` (qualification of skills with evidence packs): this compares whole agent+model configurations.

**Why Jerry:** Batch orchestration expertise and hands-on Claude Code skill-building.

**MVP:** Config matrix YAML → Batch array jobs (reusing idea 2's sandbox) → grader → HTML/Markdown report with accuracy, tokens, $ and trend vs. last run. Stack: Python, AWS Batch, Terraform, DuckDB/Parquet for results.

**Career angle:** "AI evaluation engineering" is a fast-growing role; ties to bio-domain credibility.

## 4. `s3files-nf-bench` — Terraform + benchmark of Nextflow work-dir backends on AWS (S3 Files vs Mountpoint vs Fusion vs EFS)
**Pitch:** An open, reproducible benchmark and reference Terraform for choosing the cheapest/fastest shared filesystem layer for Nextflow on AWS Batch, now that S3 Files exists.

**Problem & who needs it:** Platform engineers running nf-core pipelines must pick between S3 staging, Mountpoint, Fusion, and EFS. Costs and failure modes differ greatly, and S3 Files is new.

**Why now:** S3 Files GA on 2026-04-07 ([StorageNewsletter](https://www.storagenewsletter.com/2026/04/09/aws-launches-s3-files-making-s3-buckets-accessible-as-file-systems/), [AWS page](https://aws.amazon.com/s3/features/files)); the prior AWS guidance covers [Mountpoint with Nextflow on Batch](https://aws.amazon.com/blogs/hpc/optimize-nextflow-workflows-on-aws-batch-with-mountpoint-for-amazon-s3) and Seqera's [Fusion post](https://seqera.io/blog/optimize-nextflow-with-fusion/). My search found no Nextflow-specific S3 Files coverage.

**Prior art & gap:** My GitHub searches ("nextflow fusion", "nextflow s3 mountpoint fusion benchmark") returned no substantial benchmark repos; AWS's own material is blog-level. Caveat: absence in `gh search` is weak evidence; recheck before building. Different from earlier `omics-finops` (cost attribution) — this is a backend comparison.

**Why Jerry:** Built end-to-end cloud genomics on Batch/S3 processing 7,000+ samples at Encoded.

**MVP:** Terraform modules per backend; run 3 nf-core pipelines (e.g., rnaseq, sarek subset) on public data; collect wall time, S3 request counts, cost; publish a decision matrix. Stack: Terraform, Nextflow, AWS Batch, CloudWatch/CUR, Python plots.

**Career angle:** Publishable blog/benchmark that establishes "cloud infra for science" authority.

## 5. `ecr-attest-gate` — Signature + SBOM verification gate for bioinformatics containers on AWS Batch
**Pitch:** Sign, attest (SBOM/scan results), and *verify* every bioinformatics container before Batch will run it, with a release record for GxP.

**Problem & who needs it:** Pipelines pull dozens of third-party tool images (BioContainers, quay.io). Regulated teams need to prove which image digests ran and that they were scanned/approved.

**Why now:** ECR managed signing launched Nov 2025 ([AWS](https://aws.amazon.com/about-aws/whats-new/2025/11/amazon-ecr-managed-container-image-signing)); a third-party writeup (Aug 2026) argues verification remains unmanaged, and I found no managed SBOM generation/verification in ECR (per my search).

**Prior art & gap:** [BioContainers/specs](https://github.com/BioContainers/specs) (53★, last push 2023) covers naming, not attestation. GitHub searches for ECR signing returned only 0★ repos (e.g., [worklifesg/ecr-signing-image-build](https://github.com/worklifesg/ecr-signing-image-build)). Nothing bio-specific.

**Why Jerry:** ECR/Batch/IAM and Terraform expertise; GxP validation of pipelines.

**MVP:** Terraform for ECR pull-through cache + managed signing config; Lambda/Step Functions that scans (Inspector/Trivy), generates SBOM, attaches attestation; a preflight CLI that resolves a Nextflow config's images to digests and verifies them; evidence JSON. Stack: Terraform, Python, Trivy/Syft, Notation/AWS Signer.

**Career angle:** Supply-chain security + GxP evidence is a strong differentiator for biotech platform roles.

## 6. `sra-curator` — Agentic curation of public sequencing metadata into validated nf-core samplesheets
**Pitch:** Point an agent at GEO/SRA/ENA accessions; it harmonizes messy metadata (tissue, condition, strandedness, pairing), cites the evidence for each inference, and outputs a samplesheet only after human approval.

**Problem & who needs it:** Reusing public data means hours of manual metadata reading. Wrong inferences (strandedness, replicates) silently corrupt analyses.

**Why now:** MCP + skill ecosystems make evidence-grounded agents practical; bio-agent benchmarks are mainstreaming (signals above).

**Prior art & gap:** [nf-core/fetchngs](https://github.com/nf-core/fetchngs) (201★, active) fetches files and raw metadata but does not curate or infer. [mniederhuber/LLoMics](https://github.com/mniederhuber/LLoMics) (1★, last push May 2025) is an early LLM-curation attempt, effectively dormant. Distinct from earlier `manifest-sentry` (LIMS reconciliation): this targets *public* data.

**Why Jerry:** Ph.D. genomics background, NGS pipeline experience, MCP/Claude Code skills; knows which metadata errors hurt.

**MVP:** Python CLI + MCP server wrapping ENA/NCBI APIs; Claude produces field-level inferences with quoted source text and confidence; schema validation (samplesheet schema) and a review UI (TUI/Markdown diff); emit fetchngs-compatible CSV. Stack: Python, Pydantic, ENA/NCBI E-utilities, Claude API.

**Career angle:** Showcases human-in-the-loop agent design with provenance in a bioinformatics setting.
